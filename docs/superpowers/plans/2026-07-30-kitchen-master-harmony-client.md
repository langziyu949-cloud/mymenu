# Kitchen Master HarmonyOS Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the single-device HarmonyOS 6.1 application that records recipes through an AI conversation, stores them locally, supports later edits, and animates a confirmed recipe into the library.

**Architecture:** A Stage-model ArkTS application uses one root `Navigation` stack and three bottom destinations. View models coordinate UI state, a repository layer owns ArkData relational storage and app-private photos, and a small HTTP client talks only to the stateless backend. Recipe identifiers and timestamps are sync-ready even though MVP has no account or cloud recipe storage.

**Tech Stack:** DevEco Studio 6.1.0, HarmonyOS SDK API 23, ArkTS, ArkUI, ArkData `relationalStore`, system PhotoViewPicker/CameraPicker, `@ohos.net.http`, Hypium local tests.

## Global Constraints

- Bundle name is `com.ziyu.kitchenmaster`; product name shown to users is `厨房主理人`.
- Compile and target SDK are API 23 for the user's HarmonyOS 6.1 Mate X5.
- The project root is `harmonyos/`.
- The client requests network access but no microphone permission.
- The conversation composer has no photo button.
- Photos are selected only after the recipe draft is complete and are never sent to the backend.
- One local draft session exists at most; it survives backgrounding, process death, and fold-state changes.
- A recipe can be saved only when trimmed `name` is non-empty and at least one trimmed step exists.
- The AI can ask at most one round of up to three critical questions. The user can skip that round.
- AI-estimated amounts are marked only while reviewing the draft. Saving accepts them and removes the marker from saved UI.
- Experience is never required and is never requested when absent.
- Deleting allows a five-second undo before relational rows and the app-private photo are physically removed.
- No login, cloud sync, export, backup, or in-app motion toggle exists in MVP.
- The save motion lasts about 900 ms, targets the bottom-left `菜谱` destination, respects the system reduced-motion preference, then opens the library and highlights the new card for about 1.2 seconds.

```sql
CREATE TABLE IF NOT EXISTS recipes (
  id TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL,
  name TEXT NOT NULL,
  experience_json TEXT NOT NULL,
  photo_path TEXT,
  original_text TEXT NOT NULL,

  recipe_id TEXT NOT NULL,
  content TEXT NOT NULL,
  sort_order INTEGER NOT NULL,
  FOREIGN KEY(recipe_id) REFERENCES recipes(id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS draft_sessions (

  current_recipe_json TEXT,
  questions_asked INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

Create indexes on `recipes(name)`, `recipe_items(recipe_id, kind, sort_order)`, and `recipe_steps(recipe_id, sort_order)`.

- [ ] **Step 4: Implement transactional repositories**

`RecipeRepository.save(draft, originalText, photoPath?, recipeId?)` normalizes
the draft, rejects unsaveable data, uses the supplied preallocated UUID or
generates one, gets a stable random UUID from `LocalIdentityStore`, sets
`status = "saved"` and `version = 1`, writes the parent and ordered children in
one transaction, and sets both timestamps from one captured `Date.now()`.
Experience is encoded as a JSON string array in `recipes.experience_json`.

`LocalIdentityStore.getOrCreateOwnerId(): Promise<string>` uses Preferences key
`local_owner_id`; it creates a UUID once, calls `putSync()`, awaits `flush()`
before returning, and never derives an identity from hardware identifiers.

`update()` keeps `id`, `ownerId`, `originalText`, and `createdAt`, advances
`updatedAt`, increments `version`, and replaces ordered child rows
transactionally. It retains `isAiEstimated` as internal provenance, but saved
UI never displays that marker.

`list(query)` excludes `deleted_at IS NOT NULL`, sorts newest first, and uses parameterized `LIKE` clauses over recipe name plus `EXISTS` subqueries for item names. Never concatenate the query into SQL.

`DraftRepository.save()` serializes answers, conversation, and current recipe
into row `id = "active"`; `load()` returns `undefined` on no row or invalid
JSON; `clear()` deletes only that row.

- [ ] **Step 3: Implement the API client**

`RecipeApiClient`:

- joins `API_BASE_URL` with `/api/v1/recipes/analyze` or `/api/v1/recipes/revise`;
- exposes `health()` against unauthenticated `/api/v1/health`;
- sends JSON with `Authorization: Bearer <APP_ACCESS_TOKEN>`;
- uses a 35-second connect/read timeout;
- limits response text to 64 KB before parsing;
- validates `kind`, recipe required fields, maximum three questions, and all arrays before returning;
- maps `400`, `401`, `413`, `502`, `503`, timeouts, offline state, and malformed JSON to stable `RecipeApiErrorCode` values;
- always destroys the HTTP request in `finally`;
- never logs request bodies, recipe contents, or tokens.

- [ ] **Step 4: Add view-model-facing error copy**

Map errors to:

- offline/timeout: `网络有点忙，内容还在本机，可以稍后重试`
- 401: `AI 服务配置需要更新`
- 502: `这次整理结果不完整，请重试`
- 503: `AI 服务暂时不可用，请稍后重试`
- other: `暂时没能整理这道菜，请重试`
